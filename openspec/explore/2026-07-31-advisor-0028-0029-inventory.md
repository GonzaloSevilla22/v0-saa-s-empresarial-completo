# Inventario advisors 0028/0029 — funciones SECURITY DEFINER expuestas vía PostgREST

> **Fecha**: 2026-07-31 · **Fuente**: snapshot read-only de prod `gxdhpxvdjjkmxhdkkwyb` (`pg_proc` + `cron.job` vía MCP) tras la corrida de `get_advisors` post `billing-pro-trial`.
> **Disparador**: los advisors marcan WARN `0028_anon_security_definer_function_executable` (~56 entradas) y `0029_authenticated_security_definer_function_executable` (~94 entradas). Este doc inventaría el backlog completo y clasifica cada función por tipo de caller para que los revokes se hagan por lotes seguros, no a ciegas.
> **Acción inmediata**: migración `20260820000001_revoke_billing_trial_fn_execute.sql` (este PR, gate sign-off PO) cierra las 3 de billing del ciclo de trials.

## Método

1. Snapshot de prod: todas las funciones `public.*` con `prosecdef = true` y EXECUTE para `anon` o `authenticated` (el universo exacto que barren 0028/0029). El advisor cuenta **overloads** por separado; acá se deduplica por nombre (marcados `×2`).
2. Cross-check de callers:
   - `cron.job` (10 jobs, todos `username = postgres` → los revokes a `anon`/`authenticated` **nunca** afectan a pg_cron).
   - `pg_trigger` (funciones `RETURNS trigger` no son invocables con éxito vía PostgREST; el WARN es por el privilegio).
   - Grep estático de `.rpc('<fn>')` en `frontend/` + `supabase/functions/` (⚠ **aproximado** — unos pocos archivos no se pudieron leer; NO usar esta lista como única fuente para revocar). El backend Python llama RPCs vía asyncpg como `postgres`, no vía PostgREST — no necesita estos grants.

## Hallazgo sistémico: los revokes REGRESAN con DROP+CREATE

`check_low_margin()` y `handle_new_user()` aparecen expuestas **otra vez** pese a que `20260517000002_fix_function_search_path.sql` ya las había revocado. Causa: `CREATE OR REPLACE` conserva ACLs, pero un **`DROP FUNCTION` + `CREATE`** posterior (p.ej. para cambiar la firma, patrón anti-42725) resetea el ACL al default (`EXECUTE` a `PUBLIC`). Cualquier migración futura que recree una función revocada reabre el WARN en silencio.

**Recomendación**: cuando una migración haga DROP+CREATE de una función `SECURITY DEFINER`, debe re-aplicar el REVOKE en el mismo archivo (checklist de review), y a mediano plazo agregar un gate de CI que falle si una función `SECURITY DEFINER` nueva queda con EXECUTE para `anon`/`authenticated` sin allowlist explícita.
